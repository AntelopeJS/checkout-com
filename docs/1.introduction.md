# Introduction

`@antelopejs/checkout-com` implements `@antelopejs/interface-payment` on
Checkout.com's unified Payments API — the generation addressed with a
processing channel (`processing_channel_id`), not the legacy one.

## What maps to what

| Contract                        | Checkout.com                                                            |
| ------------------------------- | ----------------------------------------------------------------------- |
| `CreateCheckoutSession`         | `POST /hosted-payments` (Hosted Payments Page)                          |
| `GetCheckoutSession`            | `GET /hosted-payments/{id}`, then the payment it produced               |
| `CreatePayment`                 | `POST /payments` with a `token` (`tok_…`) or `id` (`src_…`) source      |
| `GetPayment`                    | `GET /payments/{id}`, plus `/actions` for a decline's reason            |
| `CapturePayment`                | `POST /payments/{id}/captures`                                          |
| `CancelPayment`                 | `POST /payments/{id}/voids`                                             |
| `RefundPayment`, `GetRefund`    | `POST /payments/{id}/refunds`; the refund is an action on the payment   |
| `CreateCustomer`, `GetCustomer` | `POST /customers`, `GET /customers/{id}`                                |
| `DeleteCustomer`                | `DELETE /customers/{id}`, which also deletes the customer's instruments |
| `ListPaymentMethods`            | The `instruments` of `GET /customers/{id}`                              |
| `DetachPaymentMethod`           | `DELETE /instruments/{id}`                                              |
| `VerifyWebhook`                 | HMAC-SHA256 `Cko-Signature` from a workflow's webhook action            |

Nothing in the contract is declined with `UnsupportedOperationError`.

### Why the Hosted Payments Page and not Payment Links

Both are hosted pages for one payment. The Hosted Payments Page is the one
Checkout.com positions for a backend that redirects the payer: it requires
success, cancel and failure URLs and returns the payer to them, it can save the
card for later (Payment Links are marked as unable to in Checkout.com's
comparison), and it can show a customer's saved cards. Payment Links are for
sending a link by email or SMS, and they leave the payer on a Checkout.com
confirmation page.

## Identifiers

Every identifier the contract hands out is Checkout.com's own, except a
refund's. Checkout.com keeps a refund as an action on its payment, readable only
through that payment, so a refund id is `<pay_…>:<act_…>`. Treat it as opaque, as
the contract asks.

An identifier that cannot be one of Checkout.com's (`pay_` and 26 characters,
and so on) is reported as not found without a call.

## Accounts

The top-level configuration is the default account. `accounts` adds more, keyed
by the name callers pass as the payment interface's trailing `provider`
argument:

```ts fragment
config: {
  secretKey: "sk_…",
  processingChannelId: "pc_…",
  accounts: {
    marketplace: { secretKey: "sk_…", processingChannelId: "pc_…", webhookSignatureKey: "…" },
  },
}
```

A call naming an account that is not configured is refused with
`PaymentError`. Each account has its own webhook keys, so a delivery verified
under one account is refused under another.

## Base URLs and keys

Checkout.com documents base URLs unique to each merchant —
`https://{prefix}.api.sandbox.checkout.com` and
`https://{prefix}.api.checkout.com`, where the prefix is the first eight
characters of the client id — and says a request to any other host is refused
with 403 `base_url_invalid`. Set `baseUrl` from the Dashboard. Without it the
module uses `https://api.sandbox.checkout.com` for an `sk_sbox_` key and
`https://api.checkout.com` otherwise; if Checkout.com refuses that host, the
error says to set `baseUrl`.

Keys are sent as `Authorization: Bearer <secret key>`.
