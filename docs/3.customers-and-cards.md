# Customers and saved cards

## Customers

Checkout.com requires an email on every customer and keeps emails unique within
an account. `CreateCustomer` without an email is refused with `PaymentError`
(`email_required`); one whose email another customer already has, with
`PaymentError` (`customer_email_already_exists`).

`/customers` takes no idempotency key. A replay is recognised at Checkout.com
instead: the module stores a fingerprint of the idempotency key in the
customer's metadata (`antelope_idempotency`), so when a replay collides with the
email its first attempt created, the customer found by that email carries the
same fingerprint and is returned. This holds across restarts and instances; a
replay that changes the email is a new customer.

Customer metadata holds at most 20 pairs. The module's own entries share that
budget with yours, and are never returned in `Customer.metadata`.

## Saved cards

A saved card is a Checkout.com instrument, `src_…`. It is saved by a payment the
payer is present for, with `savePaymentMethod` and a `customer`:

- with a token, the payment stores the card and links it to the customer;
- with an instrument that is not yet the customer's, the module links it after
  the payment.

`DetachPaymentMethod` deletes the instrument.

### The payment chain

A charge with `offSession` is a merchant-initiated transaction:
`merchant_initiated: true`, `payment_type` from `merchantInitiatedType`
(`Recurring` by default), and `previous_payment_id` — the payment that saved the
card. Checkout.com asks for that chain on every merchant-initiated charge; it can
look the first payment up itself, but says not to rely on it, and a missing
chain raises soft declines.

The contract does not carry the chain, and Checkout.com does not keep it with
the instrument, so the module keeps it in the customer's metadata, one entry per
card: `antelope_method_<src_…>` → `<pay_…> <saved at>`. The entry is written once,
after the saving payment, and read before every off-session charge of that card
for that customer.

The same entry dates the card: Checkout.com records no creation time for an
instrument, so `PaymentMethod.createdAt` is when the module saved it. A card
saved some other way — in the Dashboard, through `/instruments`, by another
integration — has no entry: its `createdAt` is 0, and its off-session charges
carry no `previous_payment_id`, which leaves the chain to Checkout.com's own
lookup. So does a card saved for a customer whose metadata is already at 20
entries.

If recording fails after the payment has gone through, the payment is still
returned — failing the call would invite a retry under a new key and a second
charge. The failure is written to stderr, and replaying the same idempotency key
records it.

### Recurring or Unscheduled

The schemes want to know what a stored card will be used for. `Recurring` (the
default) declares a series at intervals — subscriptions. `Unscheduled` declares
charges at varying times, such as a balance top-up. The setting applies to the
saving payment (as the customer-initiated start of the series) and to every
off-session charge, per account. The contract has no field for it.

## Hosted checkout

`CreateCheckoutSession` creates a Hosted Payments Page. The page needs a billing
country, which a checkout session request does not carry:
`checkoutBillingCountry` on the account provides it, and hosted checkout is
refused without it. `cancelUrl` is used as the failure URL too. `locale` is
matched to the page's languages (`fr` → `fr-FR`); one it does not have is
dropped.

### Replays

`/hosted-payments` takes no idempotency key and a page can be found again only by
its id. A replayed key returns the first session within the same process, for
the page's 24-hour lifetime, and concurrent calls with one key share a single
page. A retry after a restart, or on another instance, opens a second page.
Store the session id before redirecting the payer.

### Reading a session

| Hosted page status | Session status                                                     |
| ------------------ | ------------------------------------------------------------------ |
| `Payment Pending`  | `pending`, even after a failed attempt — the payer can still retry |
| `Payment Received` | the payment's own status                                           |
| `Expired`          | `canceled`                                                         |

`payment` is set once the page has produced a payment. (Checkout.com's own
examples return the string `"undefined"` for a page without one; it is not
treated as a payment.)

### Saving the card through the page

With `savePaymentMethod` and a `customer`, the page is asked to store the card
(`store_payment_details: enabled`) for the customer's email. The payment that
stored it is only known once the page has been paid, so it is recorded on the
customer the first time `GetCheckoutSession` reads the completed session. Until
then — or if the session is never read — the card behaves as one saved some
other way.

## Deleting a customer

`DeleteCustomer` deletes the customer and, at Checkout.com, every instrument
linked to it.
