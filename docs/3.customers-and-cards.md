## Customers

Checkout.com requires an email on every customer and keeps emails unique within
an account. `CreateCustomer` without an email fails with `PaymentError`
(`email_required`). `CreateCustomer` with an email that another customer already
has fails with `PaymentError` (`customer_email_already_exists`).

`/customers` takes no idempotency key, so the module recognises a replay at
Checkout.com instead. It stores a SHA-256 fingerprint of the idempotency key in
the customer's metadata (`antelope_idempotency`). When a replay collides with the
email that its first attempt created, the customer found by that email carries
the same fingerprint, and the module returns that customer. The check works
across restarts and instances. A replay that changes the email creates a new
customer.

Customer metadata holds at most 20 pairs. The module's own entries share that
limit with yours, and `Customer.metadata` never returns them. Keys the module
owns (`antelope_idempotency`, `antelope_method_…`) are dropped from the
metadata you pass, so a caller value is never read as one of the module's
records. The same holds for a payment's metadata and its `antelope_…` markers.

## Saved cards

A saved card is a Checkout.com instrument, `src_…`. A payment that the payer is
present for saves it, when the payment has `savePaymentMethod` and a `customer`:

- With a token, the payment stores the card and links it to the customer.
- With an instrument that is not yet the customer's, the module links it after
  the payment.

`DetachPaymentMethod` deletes the instrument.

### The payment chain

A charge with `offSession` is a merchant-initiated transaction. The module sends
`merchant_initiated: true`, `payment_type` from `merchantInitiatedType`
(`Recurring` by default), and `previous_payment_id`, the payment that saved the
card. Checkout.com asks for that chain on every merchant-initiated charge. It can
look the first payment up itself, but says not to rely on that, and a missing
chain causes more soft declines.

The contract does not carry the chain, and Checkout.com does not keep it with
the instrument. The module therefore keeps it in the customer's metadata, one
entry per card. The key is `antelope_method_<src_…>` and the value is
`<pay_…> <saved at>`, with the save time in epoch milliseconds.
The module writes the entry once, when it first sees the saving payment
authorized. That is the answer to `CreatePayment` when the payment needed no
3DS. A saving payment always asks for 3DS, though, and then comes back
`requires_action` without the card. The module marks such a payment with the
customer (`antelope_save_for`, hidden from callers) and writes the entry on the
first `GetPayment` or payment webhook after the payer is past 3DS. It reads the
entry before every off-session charge of that card for that customer.

Checkout.com replaces a customer's whole metadata on each update and has no
conditional write. Two cards recorded for one customer at the same moment would
keep only one entry, so the module writes one customer's entries one at a time.
That holds within one process. Two instances recording cards for the same
customer at the same moment can still lose one entry, and that card then charges
without `previous_payment_id` and reads `createdAt` 0.

The same entry dates the card. Checkout.com records no creation time for an
instrument, so `PaymentMethod.createdAt` is when the module saved it. A card
saved some other way has no entry. Examples are a card saved in the Dashboard,
through `/instruments`, or by another integration. Its `createdAt` is 0, and its
off-session charges carry no `previous_payment_id`, which leaves the chain to
Checkout.com's own lookup. A card saved for a customer whose metadata already
holds 20 entries gets no entry either.

If the record fails after the payment has gone through, the module still returns
the payment. Failing the call would invite a retry under a new key and a second
charge. The module writes the failure to stderr, and the next `GetPayment` of
that payment, a payment webhook, or a replay of the same idempotency key
records the card.

### `Recurring` or `Unscheduled`

The card schemes want to know what a stored card will be used for. `Recurring`
(the default) declares a series at intervals, such as subscriptions.
`Unscheduled` declares charges at varying times, such as a balance top-up. The
setting applies per account, to the saving payment as the customer-initiated
start of the series, and to every off-session charge. The contract has no field
for it.

## Hosted checkout

`CreateCheckoutSession` creates a Hosted Payments Page. The page needs a billing
country, which a checkout session request does not carry.
`checkoutBillingCountry` on the account provides it, and without it hosted
checkout fails with `PaymentError`. The module uses `cancelUrl` as the failure
URL too. It matches `locale` to the page's languages (`fr` becomes `fr-FR`) and
drops a locale that the page does not have.

### Replays

`/hosted-payments` takes no idempotency key, and a page can be found again only
by its ID. Within the same process, a replayed key returns the first session for
the page's 24-hour lifetime, and concurrent calls with one key share a single
page. A retry after a restart, or on another instance, opens a second page.
Store the session ID before you redirect the payer.

### Reading a session

| Hosted page status | Session status                                                      |
| ------------------ | ------------------------------------------------------------------- |
| `Payment Pending`  | `pending`, even after a failed attempt, because the payer can retry |
| `Payment Received` | The payment's own status                                            |
| `Expired`          | `canceled`                                                          |

`payment` is set once the page has produced a payment. Checkout.com's own
examples return the string `"undefined"` for a page without one, and the module
does not treat that string as a payment.

### Saving the card through the page

With `savePaymentMethod` and a `customer`, the module asks the page to store the
card (`store_payment_details: enabled`) for the customer's email. The page's
`payment_type` is `Recurring` when `merchantInitiatedType` is `Recurring`, and
`Regular` when it is `Unscheduled`. The module knows the payment that stored the
card only once the page has been paid. It records that payment on the customer
the first time it sees the payment, through whichever comes first:

- `GetCheckoutSession` reading the completed session.
- `VerifyWebhook` handling one of the payment's events.

Until then the card behaves as one saved some other way. The webhook path relies
on Checkout.com copying the page's metadata onto the payment it produces, which
Checkout.com documents nowhere.

## Deleting a customer

`DeleteCustomer` deletes the customer. At Checkout.com, that also deletes every
instrument linked to the customer.
