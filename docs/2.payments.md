# Payments

## Statuses

| Checkout.com                                                               | Contract                                                     |
| -------------------------------------------------------------------------- | ------------------------------------------------------------ |
| `Pending` with a redirect link                                             | `requires_action`                                            |
| `Pending`, `Retry Scheduled`                                               | `pending`                                                    |
| `Authorized`, for a payment created with `authorizeOnly`                   | `authorized`                                                 |
| `Authorized`, for a payment this module asked to capture                   | `pending` — the automatic capture has not been processed yet |
| `Captured`, `Partially Captured`, `Partially Refunded`, `Refunded`, `Paid` | `succeeded`                                                  |
| `Card Verified`                                                            | `succeeded`                                                  |
| `Declined`                                                                 | `failed`                                                     |
| `Voided`, `Canceled`, `Expired`                                            | `canceled`                                                   |

A payment made elsewhere on the account and reported `Authorized` is
`authorized`: only payments this module creates carry the marker
(`antelope_capture` in their metadata, hidden from callers) that says capture was
asked for.

The redirect link exists only on the answer to the call that created the
payment. `GetPayment` on a payment still waiting for its payer reads `pending`,
without `redirectUrl`.

## Direct payments

`CreatePayment` needs a `paymentMethod`:

- a token from Frames or Flow, `tok_…`, single use — the payer is present;
- a saved instrument, `src_…`, from `ListPaymentMethods`.

Anything else is reported as an unknown payment method. Without a
`paymentMethod` the call is refused: Checkout.com takes no payment without a
source.

`returnUrl` becomes both `success_url` and `failure_url`, where the payer comes
back after 3D Secure.

### 3D Secure

3DS is the redirect the contract already models. A payment that needs it is
answered with `202 Pending` and `_links.redirect`, reported as
`requires_action` with that link as `redirectUrl`. Send the payer there; the
outcome arrives by webhook and through `GetPayment`.

Ordinary on-session payments do not ask for 3DS; Checkout.com upgrades a payment
to 3DS by itself when the issuer requires it (`allow_upgrade` defaults to true).
A payment that saves the card asks for 3DS with
`challenge_indicator: challenge_requested_mandate`, as Checkout.com requires in
regions with strong customer authentication. Off-session payments never ask.

### Declines

A decline is a result: `CreatePayment` resolves with a `failed` payment. The
reason is Checkout.com's response code:

| Response code                     | `failure.code`          |
| --------------------------------- | ----------------------- |
| 20051, 50280                      | `insufficient_funds`    |
| 20054, 30033                      | `expired_card`          |
| 20014, 20087, 20100, 20124, 200N7 | `incorrect_details`     |
| 20150, 20151, 20154, 20155, 43401 | `authentication_failed` |
| 20152 (3DS not completed in time) | `expired`               |
| 20068, 20091, 20096, 20153, 20159 | `processing_error`      |
| anything else                     | `declined`              |

`failure.providerCode` is the response code itself. `GET /payments/{id}` carries
no response code, so `GetPayment` reads a declined payment's reason from its
authorization action.

## Authorize and capture

`authorizeOnly` sends `capture: false`. `CapturePayment` posts a capture — of the
amount given, or of everything — and `CancelPayment` a void. Checkout.com
accepts both with a 202 and applies them later, so each call reads the payment
back until the action shows, for up to `settleTimeoutMs`, and returns it as it
then stands. A capture is final: Checkout.com voids any amount left uncaptured.

Only an `authorizeOnly` payment can be captured. A payment this module asked
Checkout.com to capture by itself is refused with `InvalidPaymentStateError`
(`automatic_capture`), whatever it currently reads — the refusal rests on how the
payment was created, so a replayed capture of an `authorizeOnly` payment is still
answered as the first one was.

A payment waiting for its payer's 3DS (`requires_action`) cannot be cancelled:
Checkout.com voids only an authorization, and there is none yet. The call is
refused with `InvalidPaymentStateError`; the payment ends by itself when the
payer abandons.

Capturing or voiding a payment whose state does not allow it is refused by
Checkout.com with a bodiless 403, reported as `InvalidPaymentStateError`. So is
an action Checkout.com answers with "already captured", "already voided" or
"already refunded" (200) — a replay with the same idempotency key is answered as
the first call was, so a 200 means a different call did it.

## Refunds

`RefundPayment` posts a refund, of the amount given or of everything still
refundable. Checkout.com accepts it with a 202 and processes it later, so the
refund is usually `pending`; `refund.succeeded` or `refund.failed` follows by
webhook, and `GetRefund` reads the refund's action. A refund id whose action is
not among its payment's actions, or is not a refund, is `PaymentNotFoundError`.
Checkout.com's refund request
has no reason field; the contract's `reason` is kept in the refund's metadata as
`antelope_refund_reason`, visible in the Dashboard and hidden from callers.

A refund above the refundable balance is `InvalidPaymentStateError`. An issuer
refusing the refund outright (422 `refund_authorization_declined`) is a
`PaymentError` carrying that code.

## Errors

| Checkout.com answered                                                                                    | Raised as                                        |
| -------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| 404                                                                                                      | `PaymentNotFoundError` / `CustomerNotFoundError` |
| 403 on a capture, void or refund                                                                         | `InvalidPaymentStateError`                       |
| 403 `base_url_invalid`                                                                                   | `PaymentError` saying to set `baseUrl`           |
| 422 `amount_exceeds_balance`, `capture_value_greater_than_(remaining_)authorized`, `void_amount_invalid` | `InvalidPaymentStateError`                       |
| 422 `customer_not_found`, `customer_id_invalid`                                                          | `CustomerNotFoundError`                          |
| 422 `source_id_unknown`, `source_id_invalid`                                                             | `CustomerNotFoundError` (payment method)         |
| any other 422                                                                                            | `PaymentError` with the first error code         |
| 401, 409, 429, 5xx, a timeout or no answer at all                                                        | `PaymentError` — retry it                        |

Only an answer Checkout.com gave can become a not-found or a state error. An
outage never reads as a permanent refusal.

## Idempotency

The idempotency key is sent as `Cko-Idempotency-Key` on `/payments` and on the
capture, void and refund actions — the endpoints Checkout.com documents it for.
Checkout.com keeps a key for 72 hours, and only for a 2xx answer.
`/customers` and `/hosted-payments` take no key; see
[Customers and saved cards](./3.customers-and-cards.md) for what replaces it.

## Amounts

Amounts are minor units, as the contract's are. Checkout.com requires the last
digit of an amount in a three-decimal currency (BHD, IQD, JOD, KWD, LYD, OMR,
TND) to be 0, and the last two digits of a CLP amount to be 00. Such an amount is
legal in the contract and refused by Checkout.com with 422 `amount_invalid`,
reported as a `PaymentError`.

A `reference` may be at most 80 characters for a payment and 50 for a hosted
page (30 for American Express).
