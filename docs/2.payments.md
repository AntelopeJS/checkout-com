## Statuses

| Checkout.com                                                               | Contract                                                      |
| -------------------------------------------------------------------------- | ------------------------------------------------------------- |
| `Pending` with a redirect link                                             | `requires_action`                                             |
| `Pending`, `Retry Scheduled`                                               | `pending`                                                     |
| `Authorized`, for a payment created with `authorizeOnly`                   | `authorized`                                                  |
| `Authorized`, for a payment this module asked to capture                   | `pending`, because the automatic capture has not happened yet |
| `Captured`, `Partially Captured`, `Partially Refunded`, `Refunded`, `Paid` | `succeeded`                                                   |
| `Card Verified`                                                            | `succeeded`                                                   |
| `Declined`                                                                 | `failed`                                                      |
| `Voided`, `Canceled`, `Expired`                                            | `canceled`                                                    |
| Any other status                                                           | `pending`                                                     |

A payment made elsewhere on the account and reported `Authorized` is
`authorized`. Only payments this module creates carry the marker that says
capture was asked for. The marker is `antelope_capture` in their metadata, hidden
from callers.

The redirect link exists only on the answer to the call that created the
payment. `GetPayment` on a payment still waiting for its payer reads `pending`,
without `redirectUrl`.

## Direct payments

`CreatePayment` needs a `paymentMethod`, which is one of these:

- a single-use token from Frames or Flow, `tok_…`, for a payer who is present.
- a saved instrument, `src_…`, from `ListPaymentMethods`.

The module reports any other value as an unknown payment method, with
`CustomerNotFoundError`. Without a `paymentMethod`, the call fails with
`PaymentError`, because Checkout.com takes no payment without a source.

`returnUrl` becomes both `success_url` and `failure_url`, where the payer comes
back after 3D Secure.

### Payer authentication

3D Secure (3DS) is the redirect that the contract already models. Checkout.com
answers a payment that needs it with `202 Pending` and `_links.redirect`. The
module reports that payment as `requires_action`, with the link as
`redirectUrl`. Send the payer there. The outcome arrives by webhook and through
`GetPayment`.

Ordinary on-session payments do not ask for 3DS. Checkout.com upgrades a payment
to 3DS by itself when the issuer requires it (`allow_upgrade` defaults to true).
A payment that saves the card asks for 3DS with
`challenge_indicator: challenge_requested_mandate`, as Checkout.com requires in
regions with strong customer authentication. Off-session payments never ask.

### Declines

A decline is a result, so `CreatePayment` resolves with a `failed` payment. The
reason comes from Checkout.com's response code:

| Response code                     | `failure.code`          |
| --------------------------------- | ----------------------- |
| 20051, 50280                      | `insufficient_funds`    |
| 20054, 30033                      | `expired_card`          |
| 20014, 20087, 20100, 20124, 200N7 | `incorrect_details`     |
| 20150, 20151, 20154, 20155, 43401 | `authentication_failed` |
| 20152 (3DS not completed in time) | `expired`               |
| 20068, 20091, 20096, 20153, 20159 | `processing_error`      |
| Any other code                    | `declined`              |

`failure.providerCode` is the response code itself. `GET /payments/{id}` carries
no response code, so `GetPayment` reads a declined payment's reason from its
authorization action.

## Authorize and capture

`authorizeOnly` sends `capture: false`. `CapturePayment` posts a capture of the
amount given, or of the whole amount when you give none. `CancelPayment` posts a
void. Checkout.com accepts both with a 202 and applies them later. Each call
therefore reads the payment back until the action shows, for up to
`settleTimeoutMs`, and returns the payment as it then stands. A capture is final,
and Checkout.com voids any amount left uncaptured.

Only an `authorizeOnly` payment can be captured. The module refuses to capture a
payment that it asked Checkout.com to capture by itself, with
`InvalidPaymentStateError` (`automatic_capture`), whatever the payment currently
reads. The refusal rests on how the payment was created, so the module answers a
replayed capture of an `authorizeOnly` payment as it answered the first one.

A payment that waits for its payer's 3DS (`requires_action`) cannot be
cancelled. Checkout.com voids only an authorization, and there is none yet. The
call fails with `InvalidPaymentStateError`, and the payment ends by itself when
the payer abandons it.

Checkout.com refuses to capture or void a payment whose state does not allow it,
with a 403 that has no body. The module reports that refusal as
`InvalidPaymentStateError`. It does the same when Checkout.com answers an action
with "already captured", "already voided", or "already refunded" (200).
Checkout.com answers a replay with the same idempotency key as it answered the
first call, so a 200 means that a different call did the action.

## Refunds

`RefundPayment` posts a refund of the amount given, or of everything still
refundable. Checkout.com accepts it with a 202 and processes it later, so the
refund is usually `pending`. `refund.succeeded` or `refund.failed` follows by
webhook, and `GetRefund` reads the refund's action. A refund identifier whose
action is not among its payment's actions, or is not a refund, fails with
`PaymentNotFoundError`.

Checkout.com's refund request has no reason field. The module keeps the
contract's `reason` in the refund's metadata as `antelope_refund_reason`, which
the Dashboard shows and callers do not see.

A refund above the refundable balance fails with `InvalidPaymentStateError`. An
issuer that refuses the refund outright (422 `refund_authorization_declined`)
makes the call fail with a `PaymentError` that carries that code.

## Errors

| Checkout.com answered                                                                                    | Raised as                                         |
| -------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| 404                                                                                                      | `PaymentNotFoundError` or `CustomerNotFoundError` |
| 403 on a capture, void, or refund                                                                        | `InvalidPaymentStateError`                        |
| 403 `base_url_invalid`                                                                                   | `PaymentError` that says to set `baseUrl`         |
| Any other 403                                                                                            | `PaymentError`                                    |
| 422 `amount_exceeds_balance`, `capture_value_greater_than_(remaining_)authorized`, `void_amount_invalid` | `InvalidPaymentStateError`                        |
| 422 `customer_not_found`, `customer_id_invalid`                                                          | `CustomerNotFoundError`                           |
| 422 `source_id_unknown`, `source_id_invalid`, `instrument_not_found`                                     | `CustomerNotFoundError` (payment method)          |
| Any other 422                                                                                            | `PaymentError` with the first error code          |
| 401, 409, 429, 5xx, a timeout, or no answer at all                                                       | `PaymentError`. Retry the call.                   |

Only an answer that Checkout.com gave can become a not-found error or a state
error. An outage never reads as a permanent refusal.

## Idempotency

The module sends the idempotency key as `Cko-Idempotency-Key` on `/payments` and
on the capture, void, and refund actions. Those are the endpoints Checkout.com
documents the header for. Checkout.com keeps a key for 72 hours, and only for a
2xx answer. `/customers` and `/hosted-payments` take no key. See
[Customers and saved cards](./3.customers-and-cards.md) for what replaces it.

## Amounts

Amounts are in minor units, as the contract's amounts are. Checkout.com requires
the last digit of an amount in a three-decimal currency (BHD, IQD, JOD, KWD, LYD,
OMR, TND) to be 0, and the last two digits of a CLP amount to be 00. Such an
amount is legal in the contract. Checkout.com refuses it with 422
`amount_invalid`, which the module reports as a `PaymentError`.

A `reference` may be at most 80 characters for a payment and 50 for a hosted
page (30 for American Express).
