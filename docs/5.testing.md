# Testing

```bash
pnpm test
```

The suite runs against Checkout.com's sandbox when it has a key, and against a
stand-in when it does not. Nothing else changes between the two.

## The stand-in

`src/test/standin` is an HTTP server answering the part of Checkout.com's API
the module uses. The module talks to it over HTTP exactly as it would to
Checkout.com, through the same client, with only `baseUrl` and the key
different.

Every body it answers with starts from an example in Checkout.com's
documentation — the OpenAPI document or a docs page, fetched on 2026-10-02 —
with only the fields a request decides overridden: ids, amounts, statuses,
links. `src/test/standin/fixtures/SOURCES.md` names the source of each. Its
behaviour follows the documentation too:

- outcomes by test card, from the test-card pages: 4485 0403 7153 6584 approves
  (frictionless 3DS), 4544 2491 6767 3670 declines with 20051, 4010 0617 0000 0021
  is challenged, 4242 4242 4242 4242 declines with 20051 for an amount of 101;
- tokens through the public key only, single use, 15 minutes;
- `Cko-Idempotency-Key` honoured on `/payments` and its actions only, kept for
  2xx answers, 409 for a concurrent duplicate;
- captures, voids and refunds accepted with 202 and applied later;
- refunds of 3738 refused with 422 `refund_authorization_declined`;
- customers needing a unique email and at most 20 metadata pairs;
- the amount rules for three-decimal currencies and CLP;
- MITs refused without a non-`Regular` `payment_type`, or with an unknown
  `previous_payment_id`.

Tests can also make it misbehave (a status code, a dropped connection), play the
payer (complete a 3DS challenge, pay a hosted page), and read what was sent to
it.

A suite that passes against the stand-in proves that the module agrees with
this reading of Checkout.com's documentation, and nothing more. Where the
documentation is silent the stand-in had to choose; those choices are the first
thing a live run checks.

## Running live

```bash
CKO_SECRET_KEY=sk_sbox_… CKO_PROCESSING_CHANNEL_ID=pc_… pnpm test
```

| Variable                    | Required | Meaning                                                                                                          |
| --------------------------- | -------- | ---------------------------------------------------------------------------------------------------------------- |
| `CKO_SECRET_KEY`            | Yes      | A sandbox secret key. A production key is refused.                                                               |
| `CKO_PROCESSING_CHANNEL_ID` | Yes      | A processing channel of that account.                                                                            |
| `CKO_BASE_URL`              | No       | The merchant-specific base URL. Checkout.com documents the shared host as refused, so expect to need it.         |
| `CKO_PUBLIC_KEY`            | No       | A sandbox public key. Only it may tokenize a test card, so without it every test that charges a card is skipped. |

Setting one of the first two without the other is an error rather than a quiet
run against the stand-in.

Live, the tests that need the stand-in — faults, the payer's side of 3DS and of
the hosted page, what was sent on the wire — are skipped, and the rest read
Checkout.com directly where the module hides something (a payment's
`payment_type`, a customer's metadata).

## The conformance suite

The interface's conformance suite runs in the same project, against whichever
target is chosen. Two of its tests are skipped by name, each replaced by a test
of the same flow here (`src/test/exclusions.test.ts`):

- "forgets a deleted customer" creates a customer without an email, which this
  module refuses;
- "saves a method against a customer and lists it back" saves and then detaches
  the shared test method. On Checkout.com that method is a stored instrument and
  detaching deletes it, which would leave every later charge test without one.

## Subscriptions

`src/test/renewal.test.ts` wires `@antelopejs/payment-subscriptions` (the
version pinned in `devDependencies`, against a real MongoDB) on top of this
module and lets its clock fire a renewal with nobody calling, then checks that
the charge went out as a `Recurring` MIT chained to the payment that saved the
card.
