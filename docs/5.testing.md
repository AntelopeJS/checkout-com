```bash
pnpm test
```

The suite runs against Checkout.com's sandbox when it has a key, and against a
stand-in when it does not. Nothing else changes between the two.

## The stand-in

`src/test/standin` is an HTTP server that answers the part of Checkout.com's API
that the module uses. The module talks to it over HTTP exactly as it would to
Checkout.com, through the same client. Only `baseUrl` and the key differ.

Every body the stand-in answers with starts from an example in Checkout.com's
documentation, either the OpenAPI document or a docs page, fetched on
2026-10-02. The stand-in overrides only the fields that a request decides: IDs,
amounts, statuses, and links. `src/test/standin/fixtures/SOURCES.md` names the
source of each body. The stand-in's behaviour follows the documentation too:

- Outcomes by test card, from the test-card pages. 4485 0403 7153 6584 approves
  (frictionless 3DS), 4544 2491 6767 3670 declines with 20051, 4010 0617 0000
  0021 is challenged, and 4242 4242 4242 4242 declines with 20051 for an amount
  of 101.
- Tokens through the public key only, single use, valid for 15 minutes.
- `Cko-Idempotency-Key` honoured only on `/payments` and its actions, kept for
  2xx answers, and a 409 for a concurrent duplicate.
- Captures, voids, and refunds accepted with 202 and applied later.
- Refunds of 3738 refused with 422 `refund_authorization_declined`.
- Customers that need a unique email and hold at most 20 metadata pairs.
- The amount rules for three-decimal currencies and CLP.
- Merchant-initiated transactions (MITs) refused without a `payment_type` other
  than `Regular`, or with an unknown `previous_payment_id`.

Tests can also make the stand-in misbehave, with a status code or a dropped
connection. They can play the payer, to complete a 3DS challenge or pay a hosted
page, and read what the module sent.

A suite that passes against the stand-in proves that the module agrees with
this reading of Checkout.com's documentation, and nothing more. Where the
documentation is silent, the stand-in had to choose. Those choices are the first
thing a live run checks.

## Running live

```bash
CKO_SECRET_KEY=sk_sbox_… CKO_PROCESSING_CHANNEL_ID=pc_… pnpm test
```

| Variable                    | Required | Meaning                                                                                                                         |
| --------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `CKO_SECRET_KEY`            | Yes      | A sandbox secret key (`sk_sbox_…`). The suite refuses a production key.                                                         |
| `CKO_PROCESSING_CHANNEL_ID` | Yes      | A processing channel of that account (`pc_` followed by 26 characters).                                                         |
| `CKO_BASE_URL`              | No       | The merchant-specific base URL. Checkout.com documents the shared host as refused, so expect to need it.                        |
| `CKO_PUBLIC_KEY`            | No       | A sandbox public key. Only a public key may tokenize a test card, so without it the suite skips every test that charges a card. |

If you set one of the first two without the other, the suite fails with an
error. It does not run against the stand-in instead.

In a live run, the suite skips the tests that need the stand-in: faults, the
payer's side of 3DS and of the hosted page, and what the module sent. The other
tests read Checkout.com directly where the module hides something, such as a
payment's `payment_type` or a customer's metadata.

## The conformance suite

The interface's conformance suite runs in the same project, against whichever
target the run chose. `src/test/exclusions.test.ts` skips two of its tests by
name, and a test of the same flow in this suite replaces each:

- "forgets a deleted customer" creates a customer without an email, which this
  module refuses.
- "saves a method against a customer and lists it back" saves and then detaches
  the shared test method. On Checkout.com that method is a stored instrument and
  detaching deletes it, which would leave every later charge test without one.

## Subscriptions

`src/test/renewal.test.ts` wires `@antelopejs/payment-subscriptions` on top of
this module, at the version that `devDependencies` pins and against a real
MongoDB. Its clock fires a renewal with nobody calling. The test then checks that
the charge went out as a `Recurring` MIT chained to the payment that saved the
card.
