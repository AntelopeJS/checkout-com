```bash
pnpm test
```

The suite runs against Checkout.com's sandbox when it has a key, and against a
stand-in when it does not. Nothing else changes between the two.

## The stand-in

`src/test/standin` is an HTTP server that answers the part of Checkout.com's API
that the module uses. The module talks to it over HTTP exactly as it would to
Checkout.com, through the same client. Only `baseUrl` and the key differ.

Every body the stand-in answers with starts from an example in Checkout.com's
documentation, either the OpenAPI document or a docs page, fetched on
2026-10-02. The stand-in overrides only the fields that a request decides: IDs,
amounts, statuses, and links. `src/test/standin/fixtures/SOURCES.md` names the
source of each body. The stand-in's behaviour follows the documentation too:

- Outcomes by test card, from the test-card pages. 4485 0403 7153 6584 approves
  (frictionless 3DS), 4544 2491 6767 3670 declines with 20051, 4010 0617 0000
  0021 is challenged, and 4242 4242 4242 4242 declines with 20051 for an amount
  of 101.
- A redirect for every payment that asks for 3DS on an enrolled card, as the
  sandbox answers (observed 2026-11-10). Opening the redirect authenticates a
  frictionless card; a challenged card waits for the payer's answer. Until then
  the payment answers with the redirect link and no `source`.
- Tokens through the public key only, single use, valid for 15 minutes.
- `Cko-Idempotency-Key` honoured only on `/payments` and its actions, kept for
  2xx answers, and a 409 `duplicate_request` for a duplicate sent while the
  first is in flight. The sandbox answers such a duplicate either with the
  first payment or with that 409 (observed 2026-11-10: 7 of 8 concurrent pairs
  got the payment twice, 1 got the 409); a retry under the same key then gets
  the payment.
- Captures, voids, and refunds accepted with 202 and applied later.
- An issuer's outright refusal of a refund, 422 `refund_authorization_declined`
  as documented, when a test asks for it. The sandbox has no trigger for it: it
  approved a refund of 3738 (observed 2026-11-10).
- Customers that need a unique email and hold at most 20 metadata pairs.
- Merchant-initiated transactions (MITs) refused without a `payment_type` other
  than `Regular`, or with an unknown `previous_payment_id`.

Tests can also make the stand-in misbehave, with a status code or a dropped
connection. They can play the payer, to complete a 3DS challenge or pay a hosted
page, and read what the module sent.

A suite that passes against the stand-in proves that the module agrees with
this reading of Checkout.com's documentation, and nothing more. Where the
documentation is silent, the stand-in had to choose. Those choices are the first
thing a live run checks.

## Running live

```bash
CKO_SECRET_KEY=sk_sbox_… CKO_PROCESSING_CHANNEL_ID=pc_… pnpm test
```

| Variable                    | Required | Meaning                                                                                                                                         |
| --------------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `CKO_SECRET_KEY`            | Yes      | A sandbox secret key (`sk_sbox_…`). The suite refuses a production key.                                                                         |
| `CKO_PROCESSING_CHANNEL_ID` | Yes      | A processing channel of that account (`pc_` followed by 26 characters).                                                                         |
| `CKO_BASE_URL`              | No       | The merchant-specific base URL. Checkout.com documents the shared host as refused, so expect to need it.                                        |
| `CKO_PUBLIC_KEY`            | No       | A sandbox public key. Only a public key may tokenize a test card, so without it the suite skips every test that charges a card.                 |
| `CKO_BROWSER`               | No       | A Chrome or Chromium binary. The suite opens 3DS redirects in it headless to play the payer; without it, it skips every test that saves a card. |

If you set one of the first two without the other, the suite fails with an
error. It does not run against the stand-in instead.

In a live run, the suite skips the tests that need the stand-in: faults, the
payer's side of 3DS and of the hosted page, and what the module sent. The other
tests read Checkout.com directly where the module hides something, such as a
payment's `payment_type` or a customer's metadata.

A sandbox account without balance accepts every refund with a 202 and then
fails it with response code 50003 ("Balance reservation insufficient funds").
Before the tests, a live run refunds one probe charge. When that refund fails
with 50003, the three tests that need a refund to succeed skip, and the suite
writes `not verified live: sandbox balance (50003): <test>` to stderr for each:
"reports a refund pending until Checkout.com processes it", "reports an
issuer's refusal of the refund as a failed call", and the conformance suite's
"refunds part of a captured payment". On an account with balance, or when the
probe cannot tell, they run. An over-refund is refused before any balance is
reserved, so "refuses to refund more than was captured" always runs.

## Verifying a change against the sandbox

The repository's verification skill, `.agents/skills/verify-module`, loads the
module in a project the way an application does and calls it through core. It
needs a sandbox account: without the four keys below in the environment of
`antelopejs-verify new`, every journey reads NOT VERIFIED.

```bash
set -a; . ./checkout-com.env; set +a
export CKO_BROWSER=/path/to/chrome
node_modules/.bin/antelopejs-verify new --base origin/main --title "<PR title>"
node_modules/.bin/antelopejs-verify journey <run> --plan
node_modules/.bin/antelopejs-verify clean <run>
```

Load the keys from a file, as above, so that they stay out of the shell history,
and keep them exported for every `journey` command.

| Variable                    | Required | Meaning                                                                                                   |
| --------------------------- | -------- | --------------------------------------------------------------------------------------------------------- |
| `CKO_SECRET_KEY`            | Yes      | A sandbox secret key (`sk_sbox_…`). Any other key ends each journey NOT VERIFIED.                         |
| `CKO_PUBLIC_KEY`            | Yes      | A sandbox public key (`pk_sbox_…`), which mints the test cards' tokens.                                   |
| `CKO_PROCESSING_CHANNEL_ID` | Yes      | A processing channel of that account.                                                                     |
| `CKO_BASE_URL`              | Yes      | The merchant-specific sandbox URL, `https://{prefix}.api.sandbox.checkout.com`. Any other URL is refused. |
| `CKO_BROWSER`               | No       | A Chrome or Chromium binary that opens 3DS redirects headless. Without it, `saved-card` is NOT VERIFIED.  |

Most journeys run twice: against the sandbox, then against a fresh stand-in. On
the sandbox they read what Checkout.com holds with the secret key, such as a
payment's status, balances and `payment_type`, or a customer's metadata. On the
stand-in they also check what the module sent where the sandbox shows nothing:
`previous_payment_id`, the 3DS request, the processing channel and the
idempotency key. A journey that needs the stand-in to play a part runs on the
stand-in only: the payer completing or failing a challenge, the payer paying a
hosted page, and an issuer refusing a refund.
`.agents/skills/verify-module/features/README.md` lists which journeys run
where.

A journey also reads NOT VERIFIED when the sandbox stops answering or answers
429 or 5xx, and when a refund fails because the account has no balance to refund
from (response code 50003). Each run creates customers and payments on the
account. The evidence holds no key and not the merchant's base URL.

## The conformance suite

The interface's conformance suite runs in the same project, against whichever
target the run chose. `src/test/exclusions.test.ts` skips two of its tests by
name, and a test of the same flow in this suite replaces each:

- "forgets a deleted customer" creates a customer without an email, which this
  module refuses.
- "saves a method against a customer and lists it back" saves and then detaches
  the shared test method. On Checkout.com that method is a stored instrument and
  detaching deletes it, which would leave every later charge test without one.

## Subscriptions

`src/test/renewal.test.ts` wires `@antelopejs/payment-subscriptions` on top of
this module, at the version that `devDependencies` pins and against a real
MongoDB. Its clock fires a renewal with nobody calling. The test then checks that
the charge went out as a `Recurring` MIT chained to the payment that saved the
card.
