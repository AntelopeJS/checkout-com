## Setting up

Checkout.com delivers events through a workflow with a webhook action. You
create the workflow in the Dashboard (_Developers_ › _Workflows_) or with
`POST /workflows`:

```json
{
  "name": "AntelopeJS payments",
  "active": true,
  "conditions": [
    {
      "type": "event",
      "events": {
        "gateway": [
          "payment_approved",
          "payment_pending",
          "payment_captured",
          "payment_declined",
          "payment_voided",
          "payment_canceled",
          "payment_expired",
          "payment_paid",
          "payment_refunded",
          "payment_refund_declined"
        ],
        "dispute": ["dispute_received"]
      }
    }
  ],
  "actions": [
    {
      "type": "webhook",
      "url": "https://example.com/payments/webhook",
      "headers": { "Authorization": "<a value you generate>" },
      "signature": { "method": "HMACSHA256", "key": "<a key you generate>" }
    }
  ]
}
```

Set `webhookSignatureKey` on the account to the signature key. If you gave the
action an `Authorization` header, set `webhookAuthorization` to its value.

From your route, pass the raw body and the headers to `VerifyWebhook`:

```ts fragment
const event = await VerifyWebhook({ body: rawBody, headers });
```

Checkout.com waits 10 seconds for an acknowledgement. Without one, it retries up
to eight times over about 30 hours.

## Verification

A delivery is genuine when both of these hold:

- `Cko-Signature` is the hex HMAC-SHA256 of the raw body under the signature key.
  The module compares the two in constant time and accepts either hex case.
- If `webhookAuthorization` is configured, the `Authorization` header is exactly
  that value.

Any other delivery fails with `WebhookVerificationError`. So does every delivery
to an account with no `webhookSignatureKey`. Answer 403 and act on nothing. Do
not compute the signature from a re-serialised body, because the signature covers
the bytes as they arrived.

Checkout.com signs no timestamp, so a captured delivery can be replayed and
still verify. De-duplicate on `event.id`, as the contract asks. `event.id` is
Checkout.com's `evt_…` identifier.

## The event mapping

| Checkout.com                                             | Event                | Carries                                |
| -------------------------------------------------------- | -------------------- | -------------------------------------- |
| `payment_approved`, for an `authorizeOnly` payment       | `payment.authorized` | The payment                            |
| `payment_approved`, for a payment captured automatically | None (`undefined`)   | The capture's own event follows        |
| `payment_pending`                                        | `payment.pending`    | The payment                            |
| `payment_captured`, `payment_paid`                       | `payment.succeeded`  | The payment                            |
| `payment_declined`                                       | `payment.failed`     | The payment, with the decline's reason |
| `payment_voided`, `payment_canceled`, `payment_expired`  | `payment.canceled`   | The payment                            |
| `payment_refunded`                                       | `refund.succeeded`   | The refund                             |
| `payment_refund_declined`                                | `refund.failed`      | The refund                             |
| `dispute_received`                                       | `dispute.opened`     | The dispute                            |
| Any other type                                           | None (`undefined`)   | Answer 200                             |

Partial captures and partial refunds arrive as the same event types as full
ones.

`refund.id` is the identifier that `RefundPayment` returned, so you can match the
two.

`createdAt` is the delivery's `created_on`. Some of Checkout.com's event types
use `timestamp` instead, and the module reads that field for them.

### Where each field comes from

The signature covers the whole body, so the module reads the event type, a
refund, and a dispute from the body. A payment event's body describes the action
rather than the payment. It has no creation time, and only some types carry
balances. The module therefore reads the payment back from the API, which is
equally authenticated. The event carries the payment as it stands when the
module handles the delivery, which may be later than the moment the event
describes. A `payment.authorized` delivered late can carry a payment that has
since been captured.

Because the module reads the payment back, a payment event can fail to verify
for a reason other than its signature. Checkout.com can be unreachable, or the
payment can be one this account does not have. `VerifyWebhook` then rejects with
a `PaymentError`, or `PaymentNotFoundError` for an unknown payment, and not with
`WebhookVerificationError`. Answer with a 5xx, and Checkout.com delivers again.

A payment event for a card saved on a hosted page also records that card on its
customer. See [Customers and saved cards](./3.customers-and-cards.md).

A delivery that verifies but is not JSON fails with a `PaymentError` too. So does
a JSON delivery that is not an event envelope with `id`, `type`, and a `data`
object.
