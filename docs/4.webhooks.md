# Webhooks

## Setting up

Checkout.com delivers events through a workflow with a webhook action, created
in the Dashboard (_Developers_ › _Workflows_) or with `POST /workflows`:

```json
{
  "name": "AntelopeJS payments",
  "active": true,
  "conditions": [
    {
      "type": "event",
      "events": {
        "gateway": [
          "payment_approved",
          "payment_pending",
          "payment_captured",
          "payment_declined",
          "payment_voided",
          "payment_canceled",
          "payment_expired",
          "payment_paid",
          "payment_refunded",
          "payment_refund_declined"
        ],
        "dispute": ["dispute_received"]
      }
    }
  ],
  "actions": [
    {
      "type": "webhook",
      "url": "https://example.com/payments/webhook",
      "headers": { "Authorization": "<a value you generate>" },
      "signature": { "method": "HMACSHA256", "key": "<a key you generate>" }
    }
  ]
}
```

Configure the account with `webhookSignatureKey` set to the signature key, and
`webhookAuthorization` set to the header value if you gave one.

From your route, pass the raw body and the headers to `VerifyWebhook`:

```ts
const event = await VerifyWebhook({ body: rawBody, headers });
```

Checkout.com waits 10 seconds for an acknowledgement, then retries up to eight
times over about 30 hours.

## Verification

A delivery is genuine when:

- `Cko-Signature` is the hex HMAC-SHA256 of the raw body under the signature key
  (compared in constant time, either hex case), and
- when `webhookAuthorization` is configured, the `Authorization` header is
  exactly that value.

Anything else is `WebhookVerificationError`: answer 403 and act on nothing.
Compute nothing from a re-serialised body: the signature covers the bytes as they
arrived.

Checkout.com signs no timestamp, so a captured delivery can be replayed and
still verify. De-duplicate on `event.id`, as the contract asks; it is
Checkout.com's `evt_…` id.

## The event mapping

| Checkout.com                                             | Event                | Carries                                |
| -------------------------------------------------------- | -------------------- | -------------------------------------- |
| `payment_approved`, for an `authorizeOnly` payment       | `payment.authorized` | the payment                            |
| `payment_approved`, for a payment captured automatically | — (`undefined`)      | the capture's own event follows        |
| `payment_pending`                                        | `payment.pending`    | the payment                            |
| `payment_captured`, `payment_paid`                       | `payment.succeeded`  | the payment                            |
| `payment_declined`                                       | `payment.failed`     | the payment, with the decline's reason |
| `payment_voided`, `payment_canceled`, `payment_expired`  | `payment.canceled`   | the payment                            |
| `payment_refunded`                                       | `refund.succeeded`   | the refund                             |
| `payment_refund_declined`                                | `refund.failed`      | the refund                             |
| `dispute_received`                                       | `dispute.opened`     | the dispute                            |
| anything else                                            | — (`undefined`)      | answer 200                             |

Partial captures and refunds arrive as the same event types as full ones.

`refund.id` is the identifier `RefundPayment` returned, so the two can be
matched.

`createdAt` is the delivery's `created_on` — or `timestamp`, the field some of
Checkout.com's event types use instead.

### Where each field comes from

The signature covers the whole body, so the event type, a refund and a dispute
are read from it. A payment event's body describes the action rather than the
payment — no creation time, and balances only on some types — so the payment is
read back from the API, which is equally authenticated. It is therefore the
payment as it stands when the delivery is handled, which may be later than the
moment the event describes: a `payment.authorized` delivered late can carry a
payment that has since been captured.

Reading the payment back means a payment event can fail to verify for a reason
other than its signature: Checkout.com unreachable, or a payment this account
does not have. `VerifyWebhook` then rejects with a `PaymentError` —
`PaymentNotFoundError` for an unknown payment — not with
`WebhookVerificationError`; answer with a 5xx and Checkout.com delivers again.

A payment event for a card saved on a hosted page also records that card on its
customer (see [Customers and saved cards](./3.customers-and-cards.md)).

A delivery that verifies but is not JSON is a `PaymentError` too.
